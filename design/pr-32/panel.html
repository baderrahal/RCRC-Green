One description, as many sheets as its views need

This is a mockup drawn by hand from the code in src/RcrcGreen.Revit/DrawingSheetPanel.cs. It is not a screenshot.

Nothing on this page has been rendered by Revit or by WPF. It cannot show what an editable ComboBox drops down like, how a four column table wraps at the panel's real width, whether the warning line under a number box pushes its row out of step with the one beside it, or what the real fonts and spacing come out as.

It exists so the layout and the wording can be read before someone spends an install on it. If anyone ever describes it as a screenshot, it has stopped being worth having.

What changed

A definition used to carry one typed name and make one sheet per plot, leaving every view past the count off it. That put a sheet called GENERAL ARRANGEMENT LAYOUT around a location key plan and left five schedules unmade with a report line as the only trace. The views divide into as many sheets as they need now: six views at one per sheet is six sheets, at two is three, at four is two, and no view is ever left off. Views go onto sheets in the order they are ticked.

A sheet holding one view is named after it, the bracketed code removed and the rest upper cased, the way the team's own sheets read. Its number continues the plot's own pattern: the view code, the plot's letter read off the numbers the plot already has, then the first letter not in use anywhere. DM-11's real numbers are 010QE, 010QF, 010QG, 010QH, 200Q, 400Q, 600QC and 600QD, so its letter is Q. Both are proposals in editable boxes, never demands, and a plot with no sheet numbers gets an empty box with the reason instead of an invention.

Step 4, light theme

Two view types are ticked in step 2, in this order: (200) General Arrangement Layout, then (010) Location Key Plan. Plots DM-11 and DM-12 are ticked, and DM-12 has no sheets yet. The user has typed 200QA into DM-12's first row, which clashes with the proposal above it, and both rows say so. Every name and number below except that one is a proposal.

Where the values come from

The division is SheetDivision, the name is SheetNaming and the number is SheetNumbers.Propose, all in Core with tests. One set of taken numbers is threaded through every row of every described sheet, so two proposals on one panel can never offer the same number. Typing into a box files the value under the plot and the sheet's own views, so an edit survives the redraw, and the run report says of every sheet which of its two values were generated and which were typed.

A keystroke refreshes every other box's proposal and warning without rebuilding the table, because rebuilding the tree under the cursor takes the cursor out of the box. A proposal that another row has since taken moves to the next free letter, and the box shows the move.

Nothing else in the panel changed

The grid, the sweeps, the column headers and the scope box counts are exactly as the last Drawing Sheet round left them. This round is step 4, the run line, and the two reports saying where every viewport landed.
