Drawing Sheet, step 3 after the four interface faults

This is a mockup drawn by hand from the code in src/RcrcGreen.Revit/DrawingSheetPanel.cs. It is not a screenshot.

Nothing on this page has been rendered by Revit or by WPF. It cannot show whether a borderless button really reads as a label, whether the frozen plot column stays in step with the scrolling cells once those buttons are in it, how a restored scroll offset behaves under a real mouse, what the real fonts come out as, or whether the box characters in the grid have a glyph in the font Revit uses.

It exists so the layout and the wording can be read before someone spends an install on it. If anyone ever describes it as a screenshot, it has stopped being worth having.

What changed

Four faults, found by using the panel rather than by reading it. Ticking a view type near the bottom of the list threw the list back to the top. There was no way to mark more than one cell, and 17 plots by 8 view types is 136 clicks. Eight ticked view types ran the column headers off the right edge. The legend was the one part that read well, so it is untouched.

Step 3 open, eight view types ticked

The header is the code alone wherever the code is unique, so eight columns fit across a docked pane. Code 010 is used twice in this model with two different view names, so those two headers carry the first word that tells them apart, and the key under the grid says what each shortened one stands for. The full name is on the tooltip as well.

The three ways to mark more than one cell

The dotted underline above marks what takes a click. It is not drawn in the panel, where a plot name and a column header are ordinary labels sitting inside a borderless button with the pointer set to a hand. Both were labels before and both still read as labels.

  • Mark every missing takes every empty square on every ticked plot.
  • A plot name takes that plot's whole row.
  • A column header takes that view type down every ticked plot.

All three go through BulkMarking in Core, which returns only cells a single click on the grid would have marked. A square holding a view is never swept up, because marking says a view is wanted and that one is there. An unticked plot is never swept up either, because the run does not act on it and the marks would be dropped without a word. DM-13 above is unticked, so none of the three touches it, and its squares stay empty.

The status line afterwards reads 12 cells marked, 12 in total. Marking records intent and changes nothing until Run. A sweep that finds nothing says so rather than going quiet.

The list that stays where it was left

Not drawable here, because it is a behaviour rather than a layout. Step 2 is thrown away and built again on every tick, and a new ScrollViewer starts at the top, so ticking the eightieth view type of 84 threw the list back to the first. The offset is now kept by name across the rebuild and restored on the first layout pass. It is restored then rather than on Loaded because a ScrollViewer that has not measured its content clamps any offset to zero, which would read exactly like a restore that worked. Step 1's plot list had the same fault and gets the same treatment.
